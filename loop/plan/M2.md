# M2 · 红蓝对抗（让系统自己找茬，而且找的茬必须能被检验）

## 〇、本阶段人话目标

现在系统只会"往前冲"：提方案、跑实验、看分数。它不会回头问"我选出的最优，会不会只是运气好？"

这一阶段加一支红队，专门质疑当前最优方案；蓝队负责执行检验。
**关键约束：红队的质疑必须是"可被代码检验的"**，不接受"我觉得可能过拟合"这种没法验证的话。

做完之后应该能看到这样的画面：
```
红队质疑：最优方案 histgb 的分数可能是 seed 运气
检验方式：换 3 个 seed 重跑，看分数标准差是否 > 0.02
蓝队结论：std=0.004 → 质疑不成立，维持最优
```
或者：
```
蓝队结论：std=0.031 → 质疑成立 → 触发回滚到上一版
```

## 一、口径

- **红队只有一种合法输出**：`{claim, check_kind, check_params, threshold}`。
  - `check_kind` 必须是系统已实现的检验器之一（见下文），不许自创
  - 没有 `check_kind` 的质疑一律丢弃，记为 `rejected_vague`
- **蓝队只按数字判**，不让模型参与判定。模型只负责把结果讲成人话。
- 质疑成立 → 调 M1 的 `VersionChain.rollback()`，形成闭环。

## 二、开工前必做

1. `git status` 看清楚工作区（M1 可能刚提交完）。
2. 读：`agents.py`（看现有角色）、`evoundo.py`（M1 产物）、`research_loop.py` 主循环。
3. **先确认 M1 已完成**（`progress.log` 里有 `M1 · 完成`）。没完成就不要开工 M2。

## 三、具体实施步骤

1. **新建 `redteam.py`**：
   - `CHECKS` 注册表，至少实现三个检验器：
     - `seed_stability(proposal, n_seeds=3)` → 换 seed 重跑，返回 `std`
     - `feature_ablation(proposal, drop=1)` → 去掉最关键的一个特征重跑，返回 `delta`
     - `split_shift(proposal, n_splits=3)` → 换划分重跑，返回 `mean / std`
   - `RedTeam.propose(profile, best_version, timeout)` → 用本地模型产 1~3 条质疑，**用 JSON 约束输出**
   - `BlueTeam.verify(claim, session)` → 执行 `check_kind`，返回 `{passed, measured, threshold, detail}`
2. **接进 `research_loop.py`**：每轮实验后（或结束时）跑一次对抗，事件记 `redteam_claim` / `blueteam_verdict`。
3. 质疑成立时调 `chain.rollback()`，事件记 `rollback_triggered_by: "redteam"`。

## 四、真实测试与验收判据（不许改宽）

1. `tests/test_redteam.py` 至少 6 条：
   - 合法质疑通过校验
   - 缺 `check_kind` → `rejected_vague`
   - 未注册的 `check_kind` → 拒绝
   - `seed_stability` 真跑（用假 session，返回固定分数）能算出 std
   - 蓝队判"成立" → 触发回滚（和 M1 联动）
   - 蓝队判"不成立" → 不回滚，最优不变
2. 全量测试 **≥ 103 passed**（M1 完成后应是 103 左右，以实际为准）
3. 真跑一次，贴出真实的 `redteam_claim` 和 `blueteam_verdict` 事件

## 五、本阶段红线

- 红队**不许**直接改最优版本（它只能提议，不能执行）
- 蓝队**不许**用模型判好坏（只看数字）
- 检验器**不许**造假（不许写死返回值）
- 质疑成立时**必须**真的回滚，不许只标记
